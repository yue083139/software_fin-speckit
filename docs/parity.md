# 兩組功能一致協議（parity）

> 本檔在 OpenSpec 組與 SpecKit 組兩個 repo **逐位元組相同**（判據：`make gate-parity SIBLING=<另一 repo 路徑>`）。
> 對應需求 P-03：兩組產出的系統功能要一致，實作期間任何改動要與另一組討論。

## 1. 規則

1. **凡改使用者可感知行為的卡**（OpenSpec 的 change／Spec Kit 的 feature），開卡時先在本檔 §4「功能清單」登記或改行，並在 §5「變更紀錄」加一行；**兩個 repo 同批改本檔**（各開一個 PR，PR 描述互相連結）。
2. 一邊的規格先定稿，另一邊**照同一行為寫自己工具格式的規格**，不互抄檔案——兩組的評分各看自己工具的產物。
3. 行為以本檔＋`docs/requirements.md` 為準；兩組各自的規格與本檔衝突時，**改規格**，或回本檔改行並通知另一組。
4. 不改行為的卡（文件、重構、門禁）不必登記。

## 2. 共用技術選型（兩組相同，降低 Demo 與比對成本）

| 層 | 選型 | 理由（屬取捨） |
|---|---|---|
| 後端 | Python 3.12、FastAPI、WebSocket、uv 管理依賴 | 階段同步需要伺服器推播；與門禁腳本同語言 |
| 試算表 | openpyxl 讀寫 xlsx | 保留原檔格式與合併儲存格，回寫填空格後仍可匯回 Google Sheets |
| 前端 | React＋Vite＋TypeScript，npm 管理 | 老師端與學生端同一套元件，以路由區分 |
| 儲存 | 伺服器記憶體；**第一期不做 JSON 快照**，伺服器重啟即清空活動（Demo 前提醒老師結束後先匯出）；快照列為第二期 | 本機模擬即可（需求 §1），不引入資料庫 |
| 執行 | 本機單一伺服器；多個瀏覽器分頁模擬老師與各組 | 需求明示不必架設對外伺服器 |

選型由第一張功能卡的 design／plan 正式寫入；若一組要偏離，先改本表並通知另一組。
