# 需求基線：Vibe Coding 課堂搶答系統

> 出處：NCU SE6005 2026 軟體工程期末專題說明（PDF，不入庫）。本檔在 OpenSpec 組與 SpecKit 組兩個 repo **逐位元組相同**，改動須兩邊同批（見 `docs/parity.md`）。判據：`make gate-parity SIBLING=<另一 repo 路徑>`。
> 需求編號是兩組規格、驗收矩陣與 PR 的共同引用鍵；**只增不改號**，作廢的條目標「作廢」保留原號。

## 1. 情境

老師用填空式學習單（Guided Notes）辦課堂搶答：活動前發給各組填寫，活動開始後收回講義，再讓學生上台把答案寫在黑板上。太耗時，故改成線上系統。只需在**本機**模擬操作，不必架設可供其他設備連線的伺服器。

## 2. 核心功能（必做）

| 編號 | 需求 |
|---|---|
| R-01 | 系統有**老師**與**學生**兩種使用者。 |
| R-02 | 老師可**匯入 Guided Notes 題目**；題數必須與 Guided Notes 一致；不要求匯入題目敘述，以題號表示即可。 |
| R-03 | 老師可**開啟、結束搶答**。 |
| R-04 | 老師可**檢視**搶答時的作答狀況與搶答結果。 |
| R-05 | 老師可把**搶答成功的組別答案匯出至原 Guided Notes**，答案須寫入原本題目的填空格中。 |
| R-06 | 學生在搶答開始後可**作答**題目。 |
| R-07 | 學生**以組別為單位送出答案**。 |
| R-08 | 學生在搶答結束後可**檢視結果**。 |
| R-09 | 學生在搶答**結束前看不到其他組別的作答狀況**。 |
| R-10 | **最快搶答的組別**選定為搶答成功的答案。 |
| R-11 | **同步所有使用者的活動階段**。 |

## 3. 額外功能（選做）

| 編號 | 需求 |
|---|---|
| X-01 | 匯入**題組**（搶答時須同時送出的題目）。 |
| X-02 | 匯出儲存活動結果（例：題號、組別答案、搶答順位）至 **CSV**。 |
| X-03 | 更公平的搶答順位機制，鼓勵還沒搶答成功的組別參與。 |
| X-04 | 其他能增進搶答活動**品質**的功能（由兩組協議後登記於 `docs/parity.md`）。 |

## 4. Guided Notes 格式

- 以 Google Sheets 形式儲存；官方提供「單題」與「題組＋單題」兩份範本，副本在 `tests/fixtures/guided-notes/`（`single.xlsx`、`group.xlsx`，以 Google Sheets「下載為 xlsx」取得）。
- **課程補充說明（2026-11-17 公告）**：「以 Google Sheets 的形式儲存」指系統需**直接串接自己雲端線上的 Google Sheets 進行讀寫**，而非下載成 .xlsx 檔在本地端離線處理。
- **負責人解讀（2026-11-17 裁，卡 `guided-notes-sheets-sync`）**：老師以 Google 帳號 OAuth 登入；匯入時先複製一份「<原標題>-搶答結果」副本，解析與寫回都對該副本，原試算表不動——副本為原 Guided Notes 的完整複本，寫入副本即滿足 R-05「匯出至原 Guided Notes」；上傳／下載 xlsx 保留為備援。
- 可自行修改範本以方便匯入／匯出（如在填空格加佔位符、題目敘述加記號）；自製測試用 Guided Notes 一律為**簡答題**。
- **禁止靜態匯入／匯出**（如「第一題答案寫到 C19」）：助教會用另一份 Guided Notes 測試。

範本實測結構（2026-11-11 下載，`make probe-guided-notes` 可重現）：

| 範本 | 表頭列 | 題號欄 | 題目欄 | 作答欄 | 題目數 |
|---|---|---|---|---|---|
| single | 第 4 列「題號／題目／作答」 | B | C:F 合併 | G:H 合併，空白 | 6 題單題，每題後隔一空白合併列 |
| group | 第 4 列「題號／題目／作答」 | B（題組跨列合併） | C:F 合併 | G:H 合併；題組子題作答格預填「（1）」「（2）」 | 4 題：第 1、2 題各 2 子題，第 3、4 題單題 |

→ 解析必須以**表頭文字定位欄位**、以**合併範圍判斷題組**，不得寫死列號與欄號。

## 5. 實作規定（兩組共同遵守）

| 編號 | 規定 |
|---|---|
| P-01 | 以 AI 代理開發，不自己撰寫程式碼；留意 AI 用量，**不要一開始就用最高級的模型**。 |
| P-02 | OpenSpec 組與 SpecKit 組各用該工具的流程製作，**各自一個 GitHub repo**。 |
| P-03 | 兩組產出的**系統功能要一致**；實作期間任何改動要與另一組討論（落點：`docs/parity.md`）。 |
| P-04 | SpecKit 組須導入 **Diagram First Development**（PlantUML 組件圖、類別圖、時序圖，存 `diagrams/` 並轉 PNG）。 |
| P-05 | 檢查 AI 生成的文件是否符合需求；系統除 AI 自動驗證外，**亦須人工驗證**（落點：各卡驗證紀錄的「人工驗證」段）。 |
| P-06 | 不得在文件、程式碼或 repo 洩漏密碼、金鑰或任何機敏資料（判據：`make gate-secrets`）。 |
| P-07 | AI 模型、框架、套件、語言、介面、流程細節皆無限制。 |

## 6. 評分重點（決定文件與流程的取捨）

- 系統檔案：文件 30%、程式碼 25%。OpenSpec 組檢驗 **proposal、spec、design、tasks**；SpecKit 組檢驗 **constitution、spec、plan、tasks、圖表**；程式碼、文件、Demo 影片須一致。
- Demo 影片 20%：每組一部、5 分鐘內、上傳 YouTube；完整展示老師端與**至少 2 組**學生端的活動流程。
- 組別評量表 15%。
- 加分：上台報告；額外功能（有創意加更多）；**以 GitHub branch／pull request 協作**；**SpecKit 組做出子功能拆分**。
- 繳交（Google 表單）：系統簡述、GitHub repo 與影片連結、**AI 對話紀錄**（落點：`docs/ai-logs/`）、實作方法與心得、小組分工表。期限 **2026-11-30（一）00:00**；逾期至 12/05 每晚一天扣 10 分。
