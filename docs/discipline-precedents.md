# 基本紀律的先例正文

本文件存放 `CLAUDE.md` 判據句背後的完整口徑、邊界與歷次裁定。`CLAUDE.md` 只留判據句，引用時**用節名不用編號**。新增先例時寫明：出處（卡名／PR 號）、日期、負責人裁定原話。

方法論移植自 hybrid_agent 專案（spec-driven、探針先行、分檔評審、互不知情的子代理評審、都綠否），2026-11-11 建立本專案時按本專案的風險面（搶答公平與作答隔離、Guided Notes 動態匯入匯出、兩組功能一致）重劃 S 檔判據。兩個 repo（OpenSpec 組、SpecKit 組）共用本檔。

## 提案品質准入六條（正文）

**適用**：S/B 檔的規格文件組（OpenSpec：proposal／design／specs／tasks；Spec Kit：spec／plan／tasks／diagrams）；第 6 條另及 C 檔改門禁的 PR；任一缺失即不許送審、不許呈批。

1. **首屏決策摘要 3–5 行**，每行「選了 X／代價 Y／可被 Z 證偽」。OpenSpec 寫在 proposal 首屏；Spec Kit 寫在 plan.md 的 Summary 段。
2. **每條設計決策帶證偽欄**，二選一：可證偽 ⇒ 附能跑的指令＋原樣輸出；不可證偽 ⇒ 明寫「屬取捨，理由 X」。OpenSpec 落在 design.md；Spec Kit 落在 plan.md 與 research.md。取捨條目就是那一輪評審的靶子，派單 §2 斷言清單從這裡取，不另編。
3. **依賴倉外行為的決策先跑探針再寫稿**：凡決策成立與否取決於第三方函式庫（openpyxl 的合併儲存格行為）、外部服務（Google Sheets 匯出格式）、瀏覽器行為（WebSocket 斷線重連）或效能，提案期先跑一個小探針，探針程式放 `probes/`，原樣輸出放 `probes/results/`。
4. **事實斷言附原樣輸出**：版本號、commit sha／tag、外部端點、行號錨四類不許憑記憶寫；憑記憶寫而被對碼推翻的，整稿退回作者重出，已用的評審輪次不退還。
5. **實作偏離提案的決策 ⇒ 回規格改稿**，按提案期規則再過；不許在 PR 裡補一句了事。作者在 PR 首屏逐條列「設計決策 → 實作落點」對照表並自報偏離。Spec Kit 組另須核對**程式與 `diagrams/` 一致**（憲章「圖表優先」）。
6. **驗收矩陣落點**：凡改使用者可感知行為、安全邊界或門禁的卡，首屏寫一行「矩陣落點」：`eval/acceptance/matrix.yaml` 新增／改哪一行，或「無落點，理由 X」；矩陣行與規格同批改。

## 提案品質：評審預算前移

提案期改一句話成本是 1，實作完再改是 100。實作期對抗輪**只找行為／隔離／契約三類**，不重開設計面；設計面的爭議必須在提案輪解決。提案常見的五類缺陷：空白偽裝成決策、事實憑記憶、依賴倉外行為未探針、驗收不可機械執行、未決事項塞給評審員。

## 都綠否的三條認綠判據

1. **報告狀態必須等於遠端狀態**：報前對碼，任一指令非 0 退出即當紅；別拿 `origin/<分支>..HEAD` 為空當判據（它只說明沒有未推送的提交，不說明遠端 CI 綠）。
2. **`make test` 按計數行認綠**：認 pytest 末行的 `N passed`、vitest 的 `Tests … passed`，缺的段報「未跑」，不數 ✅ 符號。
3. **託管側 CI 不可用時**補跑本地等價並貼原樣輸出，用正面判據認綠（如「N passed」「0 findings」），不數「跳過」。

## 作答隔離（fail-closed）

**出處**：專案建立時立（2026-11-11），對應需求 R-09 與 `CLAUDE.md` 基本紀律「作答隔離」。

**為什麼是基本紀律而不是設計選項**：搶答的公平性建立在「別組看不到我寫了什麼」。洩漏通常不在主畫面，而在旁路：WebSocket 廣播把整份狀態推給所有人、REST 回應帶了全部組別的資料只是前端沒顯示、錯誤訊息回顯答案、瀏覽器開發者工具看得到的狀態。這些旁路在正常操作下永遠看不到，只有刻意找才會露。

**判據句**：
- 伺服器送往學生端的每一則訊息與回應，都由**單一個依階段與身分裁切的函式**產生；搶答結束（階段＝已結束）之前，學生只拿得到「自己組」的作答。本專案第一期採更嚴的做法：連「哪些題已被搶答」、各題送出數與順位都不給，他組送出時本組連線也不推送任何訊息（卡 `buzz-answering` v1.1；推播時機本身會洩漏他組活動）。
- 學生身分以伺服器發出的組別憑證辨識，不採信客戶端自報的組別名稱（卡 `app-skeleton` v1.1；提案輪紅隊實證：只靠網址參數時，改參數即可在搶答中讀到他組答案）。
- 每條送往學生端的通道（每種 WebSocket 事件、每個學生可呼叫的 REST 端點）都要有負例測試：搶答中，A 組身分收到的完整 payload **不含** B 組答案字串。只斷言「畫面沒顯示」不夠，要斷言傳輸內容。
- 裁切函式拿到無法辨識的身分或階段 ⇒ 回最少資訊（視同其他組、搶答中），不得落到「回完整狀態」的預設分支。

## 搶答順位以伺服器為準

**出處**：專案建立時立（2026-11-11），對應需求 R-10。

**判據句**：順位只依伺服器**接收並寫入**的先後（同一處理序內遞增序號），不採信客戶端送來的時間戳；同一題的判定在單一臨界區內完成，並發送出時恰有一組成功。驗收須含「兩組同時送出 N 次，每次恰一組成功、順位無重號」的測試。

## Guided Notes 動態定位

**出處**：專案建立時立（2026-11-11），對應需求 §4「禁止靜態匯入／匯出」。

**判據句**：匯入以**表頭文字**（如「題號」「作答」，可設定別名）定位欄位，以**合併範圍**判斷題組與作答格；匯出寫回時以匯入時記下的「作答格位置」為準，不以題號推算座標。程式中出現寫死的儲存格座標字面量（如 `"G5"`、`row=5`）用於定位題目即為缺陷。驗收至少跑三份版面不同的 Guided Notes：官方 `single.xlsx`、`group.xlsx`，及一份**列位移、欄位移、表頭改名**的自製變形檔（夾具由匯入卡建立）。

## 創世提交（2026-11-11）

**出處**：專案初始化。

`main` 的第一個提交（治理文件＋工具初始化）由建立專案的會話直接提交並推送，不走 PR——此時 `dev` 尚不存在、也沒有可對碼的基線。**這是唯一例外**：之後所有變更（含治理文件）一律走 feature 分支→PR→`dev`。創世提交中的治理文件屬「管評審本身的文件」，按 B 檔規則應有無關方對碼；此對碼**補在第一個 PR 的評審輪一併進行**，不另開。

## pre-push 鉤子

**出處**：移植自 hybrid_agent（其 PR #1 對碼的發現與負責人裁定）。

**判據句**：兩道防線分工——①`.githooks/pre-push` 讀 Git 傳入的「遠端分支」欄，目標為 `main`／`dev` ⇒ 拒推，不看指令寫法，對所有人生效；②`.claude/settings.json` deny `Bash(git push*)`、`Bash(git * push*)` 擋 agent 的一切推送，負責人以 `!` 執行的指令不經權限層，故能推。

**它防不了什麼**：`git push --no-verify` 跳過鉤子；deny 規則比對指令字面，未列到的寫法可能漏網（agent 這樣做即違反基本紀律「並行隔離」）；沒執行 `make hooks` 的 clone 不受保護；在 GitHub 網頁上直接編輯也不經本機。repo 設為公開後可在 GitHub 端加分支保護，那才是無法繞過的一道。

## AI 用量

**出處**：需求 P-01「不要一開始就使用最高級的模型」。

**判據句**：日常實作與文件起草先用中階模型（如 Sonnet 級）；評審子代理與卡住兩輪以上的除錯才升到高階模型；每張卡的 AI 對話紀錄匯出存 `docs/ai-logs/`，供繳交與回顧用量。
